## Blueprint Architectural — Oraforme ERP

## MANIFESTE

Le moteur fiscal d'Oraforme est aujourd'hui **fragmenté** :
- La TVA est calculée en 3 endroits différents
- Les déclarations lisent des sources différentes du Grand Livre
- Les cotisations sociales n'ont aucune écriture comptable
- L'IS n'existe pas pour le pays principal
- Une taxe abolie est encore déclarée chaque mois

Ces anomalies ne sont pas des bugs. Ce sont les symptômes d'une **absence d'architecture fiscale**.

La correction de chaque anomalie isolément produira de nouvelles incohérences.

La seule solution est de poser les fondations d'abord.

**Le Foundation Fiscal Core est la loi fiscale d'Oraforme.**

Tout ce qui calcule une taxe, enregistre une taxe, déclare une taxe, ou explique une taxe doit passer par lui. Sans exception.

## 1. LES 7 LOIS FONDAMENTALES

**LOI 1 — SINGLE OWNERSHIP**
```
Toute logique fiscale appartient exclusivement au Fiscal Core.
Aucune page, aucun dashboard, aucune route API, aucun composant React
ne calcule directement un impôt ou une taxe.
```

**LOI 2 — GRAND LIVRE COMME SOURCE DE VÉRITÉ**
```
Toute déclaration fiscale est une agrégation du Grand Livre (journal_entries).
Jamais des factures. Jamais des bulletins_paie. Jamais d'une autre table.
Le Grand Livre EST la déclaration. La déclaration ne fait que le lire.
```

**LOI 3 — CALCULATEURS PURS**
```
Un FiscalCalculator est une fonction pure.
Input : montant + FiscalRule + context.
Output : FiscalAmount.
Aucun accès DB. Aucun effet de bord. Testable à l'isolation totale.
```

**LOI 4 — RÈGLES IMMUABLES ET VERSIONNÉES**
```
Une FiscalRule est une donnée, pas du code.
Elle a une date d'entrée en vigueur (effective_from).
Elle n'est jamais mutée. Elle est remplacée par une nouvelle version.
Exemple : IS_CG v1 (30%, depuis 2026-01-01) remplace IS_CG v0 (absent).
```

**LOI 5 — UN SEUL ÉCRIVAIN**
```
Le FiscalJournal est le seul composant qui écrit dans journal_entries
pour les entrées de nature fiscale.
Les triggers SQL utilisent sa logique.
Aucune route API n'insère directement une écriture fiscale.
```

**LOI 6 — ÉVÉNEMENTS COMME DÉCLENCHEURS**
```
Toute action fiscale est déclenchée par un FiscalEvent.
Un FiscalEvent est émis par l'ERP Core quand un fait économique se produit.
Le Fiscal Core réagit à l'événement. Il ne poll pas. Il ne scrape pas.
```

**LOI 7 — SÉPARATION LECTURE / ÉCRITURE**
```
L'écriture (calcul + journalisation) est séparée de la lecture (déclaration + audit).
Le chemin d'écriture : ERP → Event → Calculator → Journal → journal_entries.
Le chemin de lecture : journal_entries → Declaration Engine → Formulaire.
Ces deux chemins ne se croisent jamais.
```

### FiscalCalculator

```typescript
// lib/fiscal-core/calculators/tva.ts
// FONCTION PURE — aucun import DB autorisé dans ce fichier

function calculerTVA(
  montantHT: number,
  rule: TVAFiscalRule,
): TVACalculation {
  const tva = Math.round(montantHT * rule.taux)
  const taxes_add: Record<string, number> = {}

  for (const addRule of rule.taxes_additionnelles_resolved) {
    if (addRule.base === 'tva_collectee') {
      taxes_add[addRule.code] = Math.round(tva * addRule.taux)
    }
  }

  return {
    base_ht: montantHT,
    tva,
    taxes_additionnelles: taxes_add,
    total_ttc: montantHT + tva + Object.values(taxes_add).reduce((a, b) => a + b, 0),
    journal_writes: [
      { compte: rule.comptes.collectee, sens: 'credit', montant: tva },
      ...Object.entries(taxes_add).map(([code, montant]) => ({
        compte: rule.taxes_add_rules[code].comptes.collectee,
        sens: 'credit' as const,
        montant,
      })),
    ],
  }
}
```

### FiscalDeclaration — TVA

```
Source exclusive : journal_entries
Filtres :
  - tenant_id = $tenant
  - date_ecriture BETWEEN début_mois AND fin_mois
  - credit_account IN ('4441', '4442', '4441-CA')  → TVA collectée
  - debit_account  IN ('4445', '4446')              → TVA déductible

Agrégats :
  tva_collectee   = Σ montant WHERE credit_account IN ('4441','4442')
  ca_collecte     = Σ montant WHERE credit_account = '4441-CA'
  tva_deductible  = Σ montant WHERE debit_account IN ('4445','4446')
  tva_nette       = tva_collectee - tva_deductible
  total_a_payer   = max(tva_nette, 0) + ca_collecte

Formulaire DGI :
  l1_tva_collectee  = tva_collectee
  l2_tva_deductible = tva_deductible
  l3_tva_centimes   = ca_collecte     ← plus jamais tva_collectee × 0.05
  l4_tva_nette      = total_a_payer
```

```typescript
function calculerIRPP(
  salaireBrut: number,
  cnssDeductible: number,
  rule: IRPPFiscalRule,
): IRPPCalculation {
  const base = salaireBrut - cnssDeductible
  const baseApresAbatt = base * (1 - rule.abattement_pct)
  let irpp = 0
  let prev = 0
  for (const tranche of rule.tranches) {
    const plafond = tranche.a ?? Infinity
    const dans_tranche = Math.max(0, Math.min(baseApresAbatt, plafond) - prev)
    irpp += Math.round(dans_tranche * tranche.taux)
    prev = plafond
    if (baseApresAbatt <= plafond) break
  }
  return {
    salaire_brut: salaireBrut,
    base_imposable: baseApresAbatt,
    irpp: Math.round(irpp),
    journal_writes: [
      { compte: rule.comptes.charge, sens: 'debit',  montant: Math.round(irpp) },
      { compte: rule.comptes.retenu, sens: 'credit', montant: Math.round(irpp) },
    ],
  }
}
```

```typescript
function calculerCNSS(
  salaireBrut: number,
  rule: CNSSFiscalRule,
): CNSSCalculation {
  const branches = rule.branches
  const calcBranche = (b: CNSSBranche) => {
    const base = b.plafond ? Math.min(salaireBrut, b.plafond) : salaireBrut
    return Math.round(base * b.taux)
  }

  const cnss_salarie  = calcBranche(branches.VID_SALARIE)
  const vid_pat       = calcBranche(branches.VID_PATRONAL)
  const af_pat        = calcBranche(branches.AF_PATRONAL)
  const at_pat        = calcBranche(branches.AT_PATRONAL)
  const tus_pat       = calcBranche(branches.TUS_PATRONAL)
  const cnss_patronal = vid_pat + af_pat + at_pat + tus_pat

  return {
    cnss_salarie,
    cnss_patronal,
    branches_detail: { vid_pat, af_pat, at_pat, tus_pat },
    total: cnss_salarie + cnss_patronal,
    journal_writes: [
      { compte: '661-CNSS-SAL', sens: 'debit',  montant: cnss_salarie },
      { compte: '661-CNSS-PAT', sens: 'debit',  montant: cnss_patronal },
      { compte: '431-CNSS-SAL', sens: 'credit', montant: cnss_salarie },
      { compte: '431-CNSS-PAT', sens: 'credit', montant: cnss_patronal },
    ],
  }
}
```

```typescript
    is_theorique,
```

## 16. FISCAL EVENT BUS

**Responsabilités :**
- Recevoir les événements métier de l'ERP Core
- Les router vers les engines fiscaux appropriés
- Garantir qu'aucun événement fiscal n'est traité deux fois (idempotence)
- Logger chaque événement pour l'audit trail

**Entrées :**

**Sorties :**
```
FiscalEvent → FiscalRulesEngine (pour obtenir les règles actives)
FiscalEvent → FiscalCalculationEngine (pour calculer)
FiscalCalculation → FiscalJournal (pour écrire)
FiscalJournal → journal_entries (persistance)
FiscalEvent → FiscalAuditEngine (pour validation)
FiscalEvent → Notifications (alertes calendrier fiscal)
```

**API :**

**Consumers :**
- ERP Core (émet les événements)
- FiscalCalculationEngine (reçoit et calcule)
- FiscalJournal (reçoit les calculs et écrit)
- FiscalAuditEngine (reçoit pour validation)
- Notification Engine (alertes échéances)

**Realtime :**
- Supabase Realtime → canal `fiscal_events` → broadcast aux dashboards
- Chaque événement fiscal génère un toast "TVA journalisée — 180,000 FCFA"

**Accounting Events :**
- Chaque FiscalEvent génère 1..N journal_entries via FiscalJournal
- L'événement est lié à la source (source=event_type, source_id=payload.id)

**ERP Core :**
- Les routes API de facturation, paie, et achats émettent les événements
- La logique métier ERP ne connaît pas les comptes — elle émet juste l'événement
